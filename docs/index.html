Messy files in, checked analyses out.

Plain code reads the files and does the arithmetic, AI can draft the summary, and a separate checker compares the numbers in the draft with the computed figures and blocks the summary if one does not match. A from-scratch rebuild, on synthetic data, of part of the platform I built at StepUp & Company.

Why not just give the files to an AI model? A model can give a confident answer when a month is missing or a subtotal is wrong, and nothing in it tells you which numbers to trust. Client work needs every figure traced to its source and every gap flagged, so the split above is how I built it. Before this, a full client report at StepUp took one to two weeks (my estimate).

      AI license and access reconciler, built from IEM's posting.
      
    
      I built this after reading IEM's posting: a first version of the license and access task the role owns (provision and reclaim licenses, flag underused seats, confirm access meets governance), on synthetic data.
      
    
      Seats for people who left, and access granted without approval, pile up at onboarding and offboarding. So this grows as headcount grows. IEM has announced a $200M San Antonio plant with 3,000 jobs by 2030.1

      Why plain code, not AI
      Matching seats to the roster and the usage log follows fixed rules, so it is code I can test. The summary here is written by a template, not a model, and a separate verifier checks every number in it against the findings.
      
    
      How I would measure it
      • Seats reclaimed per month.
      • Monthly cost recovered.
      • Days from a termination to the seat being reclaimed.

      General notes: the decisions, and why I sent this.
      
  
      
  
      
    
        
      
      1. Flags, not guesses. A missing April could be filled with an average and the report would look complete. It would also hide the one thing the owner most needs to know. A flagged gap costs a phone call. A hidden estimate can cost a bad decision.
        2. 
      
      2. Plain code does the arithmetic. In the main engine Claude can draft the summary when an API key is set; every report on this site uses the plain template. One real Claude draft, checked by the verifier, is in the repo: the verifier passed it. Reading numbers, checking subtotals and doing arithmetic have exact right answers, so they are plain code I can test.
        3. 
      
      3. A separate checker. The drafter never grades its own work. If the check fails, the report says the summary was blocked and why.
        4. 
      
      4. What I would measure in production. Hours from file drop to first report. Flagged figures per run and how many a person confirmed. How often an analysis is blocked and why. How often the verifier rejects a draft.
        5. 
    
      
    
      
      
      
        
      Why I sent this to IEM
      
        
      I start with the process: how the owner really keeps the numbers. Then I build the version that works, with a separate check on it that does not trust the draft. Sheet 3 shows that check rejecting a summary with a made-up number.
